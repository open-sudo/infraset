## What this is

Start-of-session primer for any LLM working with Antrieb. Read before your first `provision`. These are the platform's contracts — follow them and commands work; ignore them and you'll rediscover the same issues every session.

## Research before theorizing

Your mental model of the platform is probably wrong in subtle ways. Before proposing a cause, gather evidence:

1. Run a diagnostic command on the actual VM.
2. Paste the output.
3. Let the evidence confirm or contradict your theory.

Cheap high-value commands: `ip -4 addr`, `ip route`, `ip neigh`, `ss -tlnp`, `systemctl is-active <svc>`, `journalctl -u <svc> -n 30 --no-pager`, `curl -v localhost:<port>`, `tcpdump -i <iface> -nn -c 10 <filter>`.

*"The platform is filtering my packets"* is a theory. *"Here is what `ip route` shows"* is evidence. Never propose an architectural fix before you've pasted the output that supports it.

## Research the appliance — use web_search / WebFetch

For specialized images (vyos, opnsense, sonic, helm-k3s, vault, terraform-aws, cloudformation-aws, ansible-controller), **fetch current docs before writing non-trivial commands**. Your training data is often 6–24 months behind. A 30-second doc fetch prevents a 10-turn debug loop of hallucinated CLI.

Workflow: look at the image's `reference` field → `web_search` for the specific topic (*"VyOS 1.5 nat source rule"*) → `WebFetch` the top result → write commands grounded in what you read.

Skip only for stable base Linux (ubuntu, alma, arch, centos, alpine). If you don't have web tools in this client, say so up front.

## Falsify before committing

When you add a rule (firewall, NAT, route, sysctl) because you think it fixes something, **prove it by removing it and confirming the issue returns**. If the problem doesn't come back without the rule, the rule was cargo-cult — delete it.

- **Start with the minimum config** that could plausibly work.
- When it doesn't work, debug with `tcpdump`/`ip route`/`conntrack -L` — don't stack more rules hoping one matches.
- For every added rule, state *why* and what evidence proves it. If you can't, it shouldn't be there.

## Fetch order for runbooks

1. `@antrieb/primer` — always (this document, fetched at session start).
2. `@antrieb/<category>-primer` — `@antrieb/networking-primer` for networking, future `@antrieb/database-primer` for DBs.
3. `search type=runbook keywords=<task>` — apply any specific-scenario match.
4. No specific match → `@antrieb/<image>-reference` for each specialized image in the topology. Won't be your exact scenario; will have current, correct syntax. **Adapt values, keep syntax.**

When the task is to create or revise an image intentionally published in the `antrieb` namespace, also fetch `@antrieb/managed-image-contract`. It is a build-time standard, not a runtime fact about similarly named images.

Never skip step 4 if step 3 matches. Never skip 1 or 2.

## Shell is POSIX sh, not bash

Every `exec` runs in `/bin/sh`. Bashisms fail, sometimes silently:

- `. /path` — not `source /path`
- `[ ... ]` — not `[[ ... ]]`
- No arrays, `${var,,}`, process substitution `<(cmd)`, `$'...'`, `set -o pipefail`
- `printf` over `echo -e`

If you genuinely need bash, write to a tempfile and invoke `bash /tmp/script.sh` explicitly.

## No TTY/PTTY

`exec` does not allocate a TTY/PTTY. Do not run commands that require an interactive terminal or automate terminal prompts through stdin. Use non-interactive alternatives: `sudo -u USER -- COMMAND` instead of interactive `su`, `chpasswd` instead of `passwd`, and package-manager flags such as `DEBIAN_FRONTEND=noninteractive` and `-y`.

Normal stdin use for pipes, heredocs, and base64 content transfer is supported.

## Cluster env vars — already set

Every exec pre-exports these. Don't re-discover:

- `NODE_NAME`, `NODE_INDEX`, `NODE_IP`
- `CLUSTER_HOSTS` — multiline `IP NAME` for every node. Drop into `/etc/hosts`:
  `echo "$CLUSTER_HOSTS" | sudo tee -a /etc/hosts`
- `CLUSTER_SSH_PUBKEY` / `CLUSTER_SSH_PRIVKEY` — per-cluster keypair for passwordless inter-node SSH:
  ```
  printf '%s\n' "$CLUSTER_SSH_PRIVKEY" > ~/.ssh/id_ed25519 && chmod 600 ~/.ssh/id_ed25519
  printf '%s\n' "$CLUSTER_SSH_PUBKEY" >> ~/.ssh/authorized_keys
  ```

## Image interfaces are exact-ANI facts

Credential files, startup scripts, helper commands, execution privilege, predefined users, and passwords are **not universal platform facts**. They apply only when the exact image returned by `search type=image` declares them in `image_interface`.

- Match the provisioned node's full ANI, including namespace and version.
- If `image_interface.credentials` exists, load its declared `path` with POSIX `.` and use only the variables listed there. Do not print secret values.
- If `image_interface.startup` exists, its declared path is the supported allocation-time helper.
- If `image_interface.execution.privilegeEscalation` is `sudo-noninteractive`, use a trusted non-interactive sudo wrapper for privileged operations. Do not infer sudo support from the operating-system name.
- If a field is absent, inspect the VM and its exact image description. Do not infer a path from a technology name such as MariaDB, PostgreSQL, Cassandra, or Vault.
- `antrieb.managed-image/v1` is a **build-time contract** for creating managed images. Its conventions are not evidence that a user-owned or otherwise undeclared image implements them.

Example: `antrieb:mariadb:v1` may declare `/etc/profile.d/antrieb-app.sh`; a user-created MariaDB image does not inherit that declaration merely because it also runs MariaDB.

## Shipping long content through exec

Anything beyond one line with quotes/newlines/metacharacters eventually breaks escaping. Use one of:

1. **Base64** (preferred): `echo <BASE64> | base64 -d > /tmp/myfile`
2. **Heredoc, unique delimiter**:
   ```
   cat > /tmp/cfg <<'ANTRIEB_EOF'
   ...
   ANTRIEB_EOF
   ```
3. **Serve between nodes**: one node runs `python3 -m http.server`, another `curl`s it.

## Streaming / long-running commands

`exec` is a synchronous await, capped at ~2 MB output. For commands that stream (`dhclient -v`, `tail -f`), run for minutes (`apt install`), or may hang, **redirect + background + poll** — the standard UNIX pattern:

```
# Launch, capture PID
exec: cmd > /tmp/out.log 2>&1 & echo $! > /tmp/cmd.pid

# Poll in subsequent exec calls (as often as you need to decide)
exec: tail -30 /tmp/out.log

# Stop early if you've seen enough
exec: kill "$(cat /tmp/cmd.pid)" 2>/dev/null
```

Each call is small and fast. The LLM decides cadence and can act on partial output turn by turn. Don't treat this as a workaround — it's the supported streaming contract.

## Small exec calls, not one huge script

One logical step per exec, check `exit_code` before the next. A 50-line script returns pass/fail with no hint of which line broke. Small steps debug easier, recover easier, and translate into runbooks cleanly.

## Provision timing

`provision` returns in under a second, but:

- Exec is available immediately.
- DHCP-assigned LAN IPs take 5–10 seconds to settle. Poll `hostname -I` until non-loopback.
- Stack-image services may still be initializing. Use `systemctl is-active <svc>` or call `startup.sh` to block until ready.

## Before you start — checklist

1. `search type=runbook` for anything relevant. **Runbooks are additive** — stack several against the same cluster.
2. `search type=image` to confirm image availability.
3. If the scenario touches networking, read `@antrieb/networking-primer`.
4. POSIX sh. Use cluster env vars. Small exec calls with exit-code checks.

<platform-reference fq_name='antrieb/networking-primer'>
## What this is

Primer for any cluster using custom `networks` or `nics` in `provision`. The default network stays out of your way; custom topologies have specific contracts. Read alongside `@antrieb/primer`.

## The default (when `networks`/`nics` are omitted)

One network named `default`:
- `/24` auto-allocated
- `egress: true` (internet over a curated port allowlist)
- `dhcp: true` (automatic addressing)
- One NIC per node

If "3 nodes that can reach each other and the internet" is the goal, use the default.

## Antrieb reserves `.1` on every DHCP-enabled network

Bridge gateway lives at `.1`; DHCP leases start at `.10`. **Don't assign `.1` to a router VM** — two hosts with the same address cause flip-flop ARP and intermittent "Host Unreachable". Use `.254` or DHCP-client the router.

## Network flags

- `egress: true` — internet reachable (port allowlist).
- `egress: false` — reaches only same-network peers. No default route out.
- `dhcp: true` — platform assigns IPs.
- `dhcp: false` — **you** assign IPs. Frames still forward at L2; "nothing pings" usually means you haven't addressed the VMs. Pick when a router VM owns addressing or you need precise /31 links.

Egress is a network property, not a node property. A node can sit on both an egress and a non-egress network (backend-behind-router pattern).

## CIDR allocation

Omit `cidr` to auto-allocate a free `/24`. Only pin when a runbook or external contract requires it — re-using a live CIDR on the same host fails. Only `/24` supported.

## `nics` assignment

If you declare `networks`, declare `nics` too, or every node lands on the first declared network:

```
"nics": {
  "node1": [{"net": "wan"}, {"net": "lan"}],
  "node2": [{"net": "lan"}]
}
```

Each list entry becomes `eth0`, `eth1`, ... (order matters).

## DHCP settling delay

`provision` returns in under a second; DHCP IPs take another 5–10s. Poll until a non-loopback address appears before exec'ing configuration:

```
for i in $(seq 1 20); do
  IP=$(hostname -I | tr ' ' '\n' | grep -vE '^(127\.|$)' | head -1)
  [ -n "$IP" ] && break; sleep 1
done
```

## Cross-cluster isolation

Every cluster is L2-isolated from every other cluster, even ones you own. Two clusters sharing a CIDR cannot reach each other. For cross-cluster traffic, go over the internet.

## Minimum config first

Networking bugs are almost always **asymmetry** (traffic takes a wrong path), not insufficient rules. Start with the minimum config that could plausibly work, then test:

- Router: one inbound-interface, one outbound-interface, masquerade on outbound.
- Firewall: default-allow in development; tighten after end-to-end flow works.
- NAT: outbound masquerade OR destination port-forward — never both stacked "just in case".

If the minimum doesn't work, **more rules won't find the asymmetry**. Compare `tcpdump -i <iface>` on both sender and receiver — where the packet changes or disappears is where to debug.

Common asymmetries, in order of frequency:

1. **Server's default gateway isn't your router.** Replies escape via the platform gateway. Fix the gateway, not the router.
2. **Wrong source interface selected.** `ip route get <peer>` — if `src` is from a stale interface (docker0, extra bridge), bring it down.
3. **`rp_filter=1` dropping asymmetric returns.** Try `sysctl net.ipv4.conf.all.rp_filter=0`.
4. **Conntrack never matched.** `conntrack -L | grep <peer-ip>` — no entry means the forward path wasn't tracked; don't add NAT rules, find why.

A rule that "makes things work" by rewriting source IPs or steering through extra hops almost always hides an asymmetry. Identify it first.

## Debugging: `tcpdump` without `-i` lies

Without `-i <iface>`, tcpdump captures everywhere and shows a NAT'd flow twice (pre- on ingress, post- on egress). Misread as "something rewrites packets on ingress". Always pin the interface.

```
tcpdump -i eth0 -nn host 1.1.1.1       # WAN side
tcpdump -i eth1 -nn host 10.10.1.10    # LAN side
```

Same source IP on both → NAT isn't being applied. Pre-NAT on one, post-NAT on the other → NAT is working.

## Debugging flowchart

1. **LAN peers can't ping each other, same `/24`:** `ip neigh show dev <iface>` — `INCOMPLETE`/`FAILED` = ARP isn't completing, usually duplicate IPs.
2. **Gateway pings, internet doesn't:** `ip route` (default route present?) and on the router check NAT rule source range.
3. **Traffic reaches router but doesn't return:** `sysctl net.ipv4.ip_forward` AND `net.ipv4.conf.<iface>.forwarding` both must be 1.
4. **"Destination Host Unreachable" from your own IP:** `ip route get <peer>` — wrong `src` interface picked; bring down the extra iface.

## Anti-patterns — wrong theories and the command that disproves them

Each: false theory → real cause → **run first**. Claim evidence, then reason.

**Family to recognize: "reconciler clobbers manual config."** Many services on these images actively manage the state you're trying to hand-configure — SONiC's `interfaces-config.service` (strips manually-assigned IPs), Ubuntu 24.04's `systemd-networkd` (removes unmanaged sub-interfaces), OpenWrt's `fw3` (regenerates firewall rules from UCI), OPNsense's `configctl system configure` (rewrites `~/.ssh/authorized_keys` from config.xml). Symptom is always the same: you set X, ten seconds later X is gone. **Fix is always the same shape:** either stop the reconciler before configuring, or express your change in the reconciler's own config language (UCI, config.xml, netplan) so it doesn't clobber. When a sub-interface or firewall rule "disappears", check for a reconciler first.

- ❌ *"The bridge filters IP when dhcp is off."* → Bridges don't filter IP by DHCP state; it's a subnet mismatch. **Run first:** `ip -4 addr` on every node, compare `/24`s.
- ❌ *"arping works but ping doesn't — bridge bug."* → `arping` is L2 broadcast; success doesn't prove IP reachability. Different subnets on one bridge route to the default gateway and die on `egress: false`. **Run first:** `ip -4 addr`, compare prefixes.
- ❌ *"The platform is rewriting my source IP on ingress."* → No platform SNAT on `egress: false`; you're capturing on all interfaces and seeing pre/post-NAT for the same flow. **Run first:** `tcpdump -i <specific_iface> -nn`.
- ❌ *"The network is broken because nothing pings."* → `dhcp: false` means you assign IPs. **Run first:** `ip -4 addr` — if only `127.0.0.1`, that's the problem.
- ❌ *"STP BPDUs mean the bridge is broken."* → Opposite; BPDUs confirm the bridge is forwarding. Look at the far-end. **Run first:** `tcpdump -i <iface> -nn host <peer-ip>` on both sides.
- ❌ *"The router's LAN interface keeps losing its IP."* → You claimed `.1` on a DHCP network; platform gateway owns it, ARP flip-flops. **Run first:** `ip neigh show dev <iface>` — reassign router to `.254`.
- ❌ *"VyOS/OPNsense ignores my iptables/nft rules."* → Appliance owns its own ruleset; direct `iptables`/`nft` corrupts it. **Run first:** `nft list ruleset | head -30` — flush raw rules and use the native CLI.
- ❌ *"'Destination Host Unreachable' from my own IP means the network is down."* → Wrong source interface picked (docker0, stale bridge). **Run first:** `ip route get <peer-ip>` — check `src`.
- ❌ *"I `ip addr add`'d a VLAN/alias/sub-interface and it disappeared 10 seconds later."* → Ubuntu 24.04's `systemd-networkd` reconciles unmanaged sub-interfaces away if it doesn't see them in its config. Same pattern as SONiC's `interfaces-config.service`. **Run first:** `systemctl stop systemd-networkd systemd-networkd.socket` on the Ubuntu host *before* manually configuring sub-interfaces. The addresses will then stick.
- ❌ *"BGP session established but no routes flow — PfxRcd=0 forever."* → Modern FRR (7.x+) enables `ebgp-requires-policy` by default. Without `no bgp ebgp-requires-policy` (or a permit route-map in each direction), sessions come up but routes are silently filtered. **Run first:** `vtysh -c "show ip bgp summary"` — if `PfxRcd=0` and session is Established, disable the policy requirement on both ends.
- ❌ *"Installed FRR on Ubuntu, configured BGP via vtysh, nothing runs."* → Ubuntu's FRR package ships with `bgpd=no` in `/etc/frr/daemons`. `vtysh` accepts BGP config but the daemon never runs. **Run first:** `grep bgpd= /etc/frr/daemons` — if it says `no`, flip to `yes`, then `systemctl restart frr`. (SONiC doesn't have this problem — its FRR runs in a docker container where `bgpd` is enabled by default.)
- ❌ *"My second NIC's `enp2s0`/`enp3s0` doesn't exist on this Ubuntu 24.04 box."* → virtio enumerates on the PCI bus libvirt assigns it, which can be 8, 9, 10, etc. — not the intuitive 2, 3. **Run first:** `ip -br link` to see the actual interface names before scripting against them.

**Rule of thumb:** before concluding "the platform is doing something weird", run `ip -4 addr` and `ip route` on every involved node. 80% of platform theories dissolve at that step.

## Checklist for custom topologies

1. Declare `networks`/`nics` only when topology itself is the thing being tested.
2. Router VMs own `.254` (or DHCP-client), never `.1`.
3. `egress: false` for networks that shouldn't reach the internet; combine with a router for controlled egress.
4. `dhcp: false` only when you're assigning IPs or running DHCP from a router VM.
5. Poll for LAN IPs before exec'ing configuration.
6. `tcpdump -i <iface>` always.

## What this is

Gold-standard **syntax reference** for VyOS on Antrieb. Fetch this when no scenario-specific VyOS runbook exists for your task. Every snippet below is a current, idiomatic VyOS block. **Copy the pattern, substitute values for your scenario.** Don't copy the example addresses, ASNs, or interface names literally — those are for illustration.

## Canonical envelope

Every config block runs inside this wrapper. **Always run it under `bash -c '...'`** — the VyOS script-template defines shell functions with hyphens in their names (e.g. `vyatta_config_commit-confirm`), which POSIX sh rejects with *"not a valid identifier"*. Since Antrieb's exec shell is `/bin/sh` (dash), the `bash -c` wrapper is required or the config will silently fail on some runs.

```
bash -c '
source /opt/vyatta/etc/functions/script-template
configure
set ...                    # your config commands
commit                     # validates and applies
save                       # persists to /config/config.boot (survives reboot)
exit
'
```

`commit` must succeed before `save`. If commit fails, fix the config and rerun; nothing sticks until commit succeeds.

**Always verify the config took effect** — `bash -c` hides `commit`'s exit status, and silent failures are possible. After the block, run `show <subsystem> rules` (e.g. `show nat destination rules`, `show firewall`) and confirm your change is present.

## Never-do list

- **Never** run `iptables`, `nft`, or edit `/etc/iptables/*` directly. VyOS owns its own nftables ruleset; direct rules fight with it and corrupt conntrack. All firewall/NAT state goes through `set firewall ...` and `set nat ...`.
- **Never** hand-edit `/config/config.boot`. Use the CLI; `save` writes it.
- **Never** assume VyOS ships with a permissive default. It doesn't. Forward traffic is dropped unless you add a firewall rule or set a default-action.

## Interface addresses

```
# Static address on a NIC
set interfaces ethernet eth1 address 10.50.50.254/24

# DHCP client
set interfaces ethernet eth0 address dhcp

# Multiple addresses on one NIC
set interfaces ethernet eth1 address 10.50.50.254/24
set interfaces ethernet eth1 address 10.50.50.1/24
```

**Antrieb-specific:** if VyOS is the LAN router, don't claim `.1` — the platform bridge owns `.1` on DHCP-enabled networks. Use `.254` (or DHCP-client and discover it).

## NAT — what you need vs what you don't

Most NAT misconfigurations on VyOS are **extra rules** added to mask a routing or gateway problem. Before writing a NAT rule, know which of these cases you're in:

### Case 1: LAN hosts → internet (the 99% case)

**You need:** one source NAT (masquerade) rule on the WAN interface, covering the LAN source range.
**You do NOT need:** anything on the LAN interface. No SNAT, no DNAT, no "return NAT". Conntrack handles reply traffic automatically.

### Case 2: External clients → internal server (port-forward / DNAT)

**You need:** one destination NAT rule on the WAN interface that rewrites the destination to the internal server.
**You do NOT need:** a source NAT on the LAN side to "make replies come back". Reply traffic is tracked by conntrack and un-NATs itself on the way out the WAN interface.

**Required invariant (the 80% failure cause):** the internal server's default route must point to VyOS's LAN IP. If the server has its gateway set to anything else (e.g., a platform-auto-assigned `.1` on a DHCP-enabled LAN that isn't VyOS), replies escape via the wrong path, VyOS never sees them, conntrack never closes the flow, and the client sees a hang. **The fix is fixing the server's default route, not adding LAN-side NAT.** Adding LAN-side NAT "works" by forcing replies to return to VyOS (because the server sees the source as VyOS's LAN IP rather than the real client), but it's a band-aid over the real asymmetry and will break other scenarios.

### Case 3: Hairpin NAT (internal client → own WAN IP → internal server)

**You need:** the same destination NAT from Case 2, plus a source NAT specifically for hairpinned traffic (source = LAN range, destination = internal server, translation = VyOS LAN IP). This is the *only* case where LAN-side SNAT is correct.

```
# Hairpin SNAT — for internal clients reaching internal servers via the WAN IP
set nat source rule 100 outbound-interface name eth1
set nat source rule 100 source address 10.50.50.0/24
set nat source rule 100 destination address 10.50.50.10
set nat source rule 100 translation address masquerade
```

### Case 4: Never needed

- SNAT on the LAN interface "to make conntrack work" — not a real thing. If the flow isn't tracked, the cause is an asymmetric path, not a missing rule.
- "Return NAT" — not a pf/nft concept; replies use existing conntrack state.
- Stacking multiple SNAT rules that cover overlapping ranges "to be safe" — they don't combine; the first match wins. Extra rules just dilute the ruleset.

Before you add a NAT rule, state out loud: *"I need this because \<specific scenario\> and without it \<specific evidence\>."* If you can't say that, don't add it.

## NAT

### Source NAT (masquerade — LAN to WAN)

```
set nat source rule 10 outbound-interface name eth0
set nat source rule 10 source address 10.50.50.0/24
set nat source rule 10 translation address masquerade
```

`rule` numbers are evaluation order (low → high). Leave gaps (10, 20, 30) so you can insert rules later.

### Destination NAT (port-forward — inbound to internal host)

```
# wan:80 → internal 10.50.50.10:8080
set nat destination rule 10 inbound-interface name eth0
set nat destination rule 10 protocol tcp
set nat destination rule 10 destination port 80
set nat destination rule 10 translation address 10.50.50.10
set nat destination rule 10 translation port 8080
```

## Firewall

Modern VyOS uses `firewall ipv4 forward filter` for transit traffic (through the router) and `firewall ipv4 input filter` for traffic to the router itself.

### Default-deny forward + explicit allows

```
set firewall ipv4 forward filter default-action drop

# Allow established/related return traffic (so outbound flows work)
set firewall ipv4 forward filter rule 5 action accept
set firewall ipv4 forward filter rule 5 state established enable
set firewall ipv4 forward filter rule 5 state related enable

# Allow HTTPS outbound from LAN
set firewall ipv4 forward filter rule 10 action accept
set firewall ipv4 forward filter rule 10 inbound-interface name eth1
set firewall ipv4 forward filter rule 10 protocol tcp
set firewall ipv4 forward filter rule 10 destination port 443

# Allow DNS outbound (HTTPS by name won't work otherwise)
set firewall ipv4 forward filter rule 20 action accept
set firewall ipv4 forward filter rule 20 inbound-interface name eth1
set firewall ipv4 forward filter rule 20 protocol udp
set firewall ipv4 forward filter rule 20 destination port 53
```

### Protect the router itself

```
set firewall ipv4 input filter default-action drop

# Allow SSH from LAN
set firewall ipv4 input filter rule 10 action accept
set firewall ipv4 input filter rule 10 inbound-interface name eth1
set firewall ipv4 input filter rule 10 protocol tcp
set firewall ipv4 input filter rule 10 destination port 22

# Allow established/related
set firewall ipv4 input filter rule 5 action accept
set firewall ipv4 input filter rule 5 state established enable
set firewall ipv4 input filter rule 5 state related enable
```

### BGP peer (eBGP between two VyOS routers)


## VRRP (active/backup failover)

```
# On primary (higher priority)
set high-availability vrrp group LAN interface eth1
set high-availability vrrp group LAN vrid 10
set high-availability vrrp group LAN priority 200
set high-availability vrrp group LAN address 10.50.50.1/24

# On backup (lower priority)
set high-availability vrrp group LAN interface eth1
set high-availability vrrp group LAN vrid 10
set high-availability vrrp group LAN priority 100
set high-availability vrrp group LAN address 10.50.50.1/24
```

Both routers ARP-advertise `10.50.50.1` via VRRP; only the priority-winner actually forwards.

## Policy-based routing (different sources use different uplinks)

```
# Define the policy
set policy route PBR-SRC rule 10 source address 10.50.50.10
set policy route PBR-SRC rule 10 set table 100
set policy route PBR-SRC rule 20 source address 10.50.50.11
set policy route PBR-SRC rule 20 set table 200

# Custom routing tables
set protocols static table 100 route 0.0.0.0/0 next-hop 203.0.113.1   # WAN1
set protocols static table 200 route 0.0.0.0/0 next-hop 198.51.100.1  # WAN2

# Attach policy to the ingress interface
set interfaces ethernet eth1 policy route PBR-SRC
```

## Zone-based firewall (named zones)

```
# Define zones
set firewall zone TRUST from UNTRUST firewall name UNTRUST-TO-TRUST
set firewall zone TRUST interface eth1
set firewall zone UNTRUST interface eth0
set firewall zone DMZ interface eth2

# Pair rules (TRUST → UNTRUST is usually allowed with state tracking)
set firewall name UNTRUST-TO-TRUST default-action drop
set firewall name UNTRUST-TO-TRUST rule 5 action accept
set firewall name UNTRUST-TO-TRUST rule 5 state established enable
```

```
show interfaces                 # all interfaces with IPs and stats
```

## Verify before concluding anything

Same rule as the networking primer: after any non-trivial config, run:

```
show interfaces                 # addresses actually assigned
show ip route                   # routes actually installed
ip -4 addr                      # kernel-level truth
ip neigh show                   # who's ARP'd
```

And from a peer: `ping`, then `curl`, then `traceroute -n`. If something misbehaves, paste the output before writing a theory.
